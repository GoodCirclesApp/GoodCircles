## Executive summary

Good Circles is **further along and broader than a "beta"** — 43 services, 35 controllers, 97 Prisma
models, 17 app views, 98 components, plus a hardened Astro marketing site. The engineering baseline
is genuinely sound in places (helmet, bcrypt-12, short-lived JWTs, zod on most write paths,
parameterized Prisma, consistent merchant/nonprofit object-ownership checks, a verified primary
Stripe webhook, HMAC-signed single-use QR tokens). But across the ecosystem there is a **focused,
fixable set of confirmed defects** that an enterprise review would block on — concentrated in
**security hardening, data-integrity/observability, in-app correctness/UX, and compliance design.**

**Overall posture: Grade C, maturity ~2.5/5 — "repeatable, not yet managed."** The marketing/public
surface is the strongest area (B / maturity 4). None of the grades count the **prerequisite-gated**
items (Stripe live keys, Stripe Connect onboarding, live payment linking, SALT-tax-consult-dependent
flows, pending business/service registrations) — those are noted, on track, and excluded per scope.

### The must-fix-before-live-money set (confirmed, NOT prerequisite-gated)

These are real, exploitable, and independent of the pending external prerequisites:

1. **JWT secret fall back to `'default_secret'`** (`tokenUtils.ts:3-4`). If the env var is ever
   unset in any environment, anyone can forge a `role:'PLATFORM'` admin token. Same pattern on the
   unsubscribe HMAC secret. → Fail-fast at boot; no fallbacks; min-entropy enforced.
2. **Catalog Stripe webhook has no signature verification** (`catalogRoutes.ts:483-508`). An
   unauthenticated attacker can POST a forged `checkout.session.completed` and mark catalog billing
   PAID without paying. → Verify with `constructEvent` like the primary webhook does.
3. **Refund IDOR** (`refundRoutes.ts` + `refundService.ts`): any authenticated user can refund any
   transaction by ID (wallet credits to the victim, debits to merchant/treasury). → Ownership/role gate.
4. **Merchant PII (Tax IDs) exposed to any authenticated user** (compliance/netting/credit endpoints,
   no role gate). → Restrict to owner/admin; redact.
5. **SSRF** via the nonprofit-controlled CRM webhook URL with no internal-egress filtering. → Block
   private/link-local ranges; allowlist schemes.
6. **No webhook/ledger idempotency** against Stripe at-least-once delivery (top-up excepted). →
   Idempotency keys + dedupe on event id.
7. **Destructive `prisma db push --accept-data-loss` on every Railway boot, with no `migrations/`
   directory** (97 models). → Baseline a migration, switch to `prisma migrate deploy`, drop the flag.
8. **Money precision**: Float used for money in catalog/analytics models; ~60% of Decimal columns
   omit precision/scale; ledger isn't cent-quantized for real settlement. → Decimal(scale 2/4) +
   rounding discipline + a conservation test to the cent.

### The enterprise-quality set (confirmed, build alongside)

- **Observability is absent** — no structured logging, request IDs, or error monitoring (Sentry).
  The central Express error handler is effectively dead code and raw `error.message` reaches clients.
- **No client-side router in the app** — the back button, refresh, and deep links are broken (the
  whole SPA is conditional rendering). Plus an auth-screen flash on refresh and **silently swallowed
  data-fetch errors** (views render empty instead of an error state).
- **Production loads Tailwind twice** (a v3 CDN dev script alongside the built v4) — ship size + FOUC.
- **In-app accuracy/brand drift** (this is the accuracy contract, *inside the product*): live in-app
  role pages render a mathematically incoherent profit/donation example and two strings say the
  nonprofit gets "10% of your purchase" (sale price) — contradicting the **10%-of-net-profit**
  contract that the marketing site states correctly. Plus the wordmark appears as "GoodCircles"
  (one word) in app copy vs. the official **Good Circles**.
- **No shared design-token system in the app** (brand CSS vars are dead; mostly ad-hoc inline
  styles), and **accessibility is largely unaddressed** app-wide (labels/ARIA/contrast/semantics).
- **Compliance design gaps**: no in-product legal pages (privacy/terms live only on marketing), no
  data-subject deletion/retention/DSAR path, and the **custodial wallet + transferable credits +
  merchant netting run unguarded** — in tension with the money-transmitter-avoidance constraint
  (feature-flag them OFF until the funded/registered phase).
- **TypeScript not in strict mode** (300+ `any`); thin tests (7 files) for a payments platform.
- **Marketing surface (the bits I shipped):** **FTC affiliate disclosure is missing on ~223 of 225
  monetized pages** (only `/partners` + get-ready carry it) — a real, quick compliance fix; plus the
  standing thin-content watch on the national "coming soon" pages.

### Prerequisite-gated (noted, on track — NOT counted against grades)

- Stripe Connect disbursement is entirely unwired (no `transfer_data`/`transfers.create`/`payouts`)
  — the largest promise-vs-code gap, but gated on Connect onboarding + business/service registration
  + the SALT consult. Refund money-movement is a stub for the same reason (and the `Transaction`
  model stores no Stripe charge id to refund against — that part *is* buildable now).
- Live Stripe keys / webhook secret swap; third-party API keys.

### What's strong (keep)

Secure-by-default password handling and admin gating with an audit log; verified primary payment
webhook with correct raw-body ordering; consistent IDOR checks in merchant/nonprofit controllers;
Decimal in the ledger split; the marketing site's SEO/GEO/schema/affiliate engineering (B/maturity 4)
with its build-time SEO regression gate.

### Where to go next

The remediation is sequenced in **`ENTERPRISE_ARCHITECTURE.md`** (target architecture + phased
roadmap to and beyond the September launch), and tracked in **`.claude/engineering_priorities.md`**
(the engineering track that previously didn't exist alongside the marketing track).

## Findings by dimension

### Cybersecurity — Grade C (maturity 2/5)

Good Circles has a sensible baseline: helmet, two-tier rate limiting, bcrypt(12) password hashing, short-lived JWT access tokens with refresh, zod validation on most write paths, Prisma (parameterized) queries, and consistently scoped object-ownership checks in the merchant/nonprofit controllers. However, several genuine, non-prerequisite security defects exist that would not pass an enterprise review. The most serious are a JWT-secret fallback to a hardcoded default ('default_secret'), a missing-or-non-blocking webhook signature verification on two webhook endpoints (catalog Stripe webhook has no verification at all; the Resend webhooks "continue" on verification failure), an IDOR in the refund route that lets any authenticated user refund any transaction by ID, and an SSRF-capable nonprofit-controlled CRM webhook URL with no internal-network egress filtering. Public marketplace endpoints also leak merchant COGS (confidential cost data). Secret hygiene at rest is good (no live keys in source, .env gitignored, admin seed requires an env password), and dependency posture is moderate (3 high / 4 moderate, all transitive/dev-leaning and fixable). The destructive `prisma db push --accept-data-loss` on every boot is an availability/integrity risk already flagged in CLAUDE.md Section 16. Overall this is "repeatable" maturity — secure-by-default in many places, but with a handful of exploitable gaps and no evidence of systematic security testing, secret rotation, or egress controls.

**Strengths**

- Passwords hashed with bcryptjs at cost factor 12 everywhere (authController, betaController, adminController, seed-admin); plaintext never stored and getProfile/updateProfile strip passwordHash before returning the user (authController.ts:248,280)
- JWT access tokens are short-lived (15m) with separate 7d refresh tokens signed with a distinct secret; refresh re-loads the user from DB (tokenUtils.ts, authController.refresh)
- Object-ownership/IDOR checks are done correctly and consistently in the merchant controller (findFirst scoped by merchantId for listings, bookings, COGS suggestions; processQrCheckout verifies merchant.id === product.merchantId) and the nonprofit controller (every handler re-resolves the caller's own nonprofit by userId)
- zod schema validation is applied on most state-changing endpoints (register, updateProfile, createListing, wallet fund/withdraw, admin issueCredits/adjustWalletBalance, governance, dms webhook) with consistent 400 handling for ZodError
- Prisma is used throughout with parameterized queries and `mode: insensitive` contains-filters; no string-concatenated SQL in user-facing paths (the only raw SQL is the startup schema guard and admin disk-usage, none of which take user input)
- Secret hygiene at rest is good: no live sk_/pk_/whsec_/re_ keys committed, .env and dist/ are gitignored, .env.example uses placeholders, and seed-admin.ts hard-fails if ADMIN_PASSWORD is unset (no default admin password)
- Admin surface is uniformly gated: adminRoutes applies authenticateToken globally plus a PLATFORM_VIEWER write-block, and every admin controller re-asserts role === 'PLATFORM'; admin mutations write to an AdminAuditLog
- Production error handler returns a generic 'Internal server error' instead of leaking stack traces/messages when NODE_ENV=production (server.ts:203-209)
- Stripe primary payment webhook (paymentController.handleWebhook) correctly verifies the signature via stripe.webhooks.constructEvent against STRIPE_WEBHOOK_SECRET with raw-body ordering set up before express.json() in server.ts
- QR checkout tokens are HMAC-signed, single-use (usedAt), 5-minute TTL, and bound to the issuing userId; CRM webhooks that the platform fires are HMAC-signed with a per-nonprofit random 32-byte secret and a request timeout

### Payments & Money-Path Functionality — Grade C (maturity 2/5)

The internal closed-loop money path (wallet-to-wallet "INTERNAL" settlement, QR in-person checkout, wallet top-up via PaymentIntent, treasury crediting) is genuinely implemented with Decimal math, a conservation model, and a documented split, and is backed by the project's two strongest test files. However, the real-dollar disbursement layer does not exist: no Stripe Connect destination charge, transfer, application fee, or payout is wired anywhere in the codebase — the Checkout Session is a plain charge to the platform account with only a transfer_group tag, and the merchant/nonprofit shares it computes are discarded. That disbursement gap is prerequisite-gated (Connect onboarding / SALT / registration) and is NOT counted against the grade. What IS counted, and what holds the grade at C, are real non-gated defects: two genuinely divergent split frames (a dead, wrong 79/10/11 frame in stripeService vs the canonical 89/10/1 net-profit frame), money stored at unbounded/fractional-cent precision with no rounding-to-cents and no Stripe-vs-ledger reconciliation, a refund money-movement stub plus a missing authorization check letting any authenticated user refund any transaction, no webhook/ledger idempotency against Stripe's at-least-once delivery, and no status/Stripe-charge-id columns on the Transaction model. The architecture is repeatable and the math engine is well-tested in isolation, but it is not yet a managed, reconciled, enterprise money system.

**Strengths**

- Canonical split lives in one place (calculateDistribution in transactionService.ts) and is reused by pricingService, paymentController, and the internal settlement path — single-sourcing the 89/10/1-of-net-profit model in the real money path.
- Decimal.js is used throughout the backend money path (calculateDistribution, walletService, refundService, pricingService) — no floating-point arithmetic in the split engine itself, avoiding drift.
- A deliberate, documented conservation model: distributed (merchantNet + nonprofitShare + platformFee + waivedContribution + creditIssued) equals the neighbor's pre-credit obligation, and a dedicated Conservation Invariant test suite asserts it to the cent across price-reduction, waived, credits, and odd-amount cases (transaction.test.ts:182-205).
- Double-entry-style ledger: every wallet movement writes a LedgerEntry with balanceAfter, and wallet.test.ts verifies credits - debits == balance and monotonic balanceAfter consistency against a real DB (honoring the 'don't mock the DB' rule).
- Platform revenue is correctly centralized in a deterministic PlatformAccount singleton (gc-platform-treasury) with its own ledger and @db.Decimal(18,4) precision, rather than an arbitrary admin wallet.
- Webhook raw-body ordering is correct: express.raw is registered for /api/payment/webhook before express.json() (server.ts:129-134), and webhook signature verification via constructEvent is present.
- Wallet top-up is correctly designed as create-PaymentIntent-then-credit-only-on-webhook (walletController.createFundIntent + completeFundFromWebhook), with a WalletTopUp row gated on status==='PENDING' so a re-fire is a no-op — the one place idempotency IS handled.
- QR in-person checkout token is HMAC-signed, single-use (usedAt), and TTL-bounded (5 min), with user-mismatch and expiry checks (qrCheckoutService.ts).

### Data Model & Database Architecture — Grade C (maturity 2/5)

The Prisma schema (97 models, 1,883 lines, single-datasource Postgres) is functionally rich and money-aware in its core ledger: it correctly uses Decimal for currency, has a singleton PlatformAccount treasury, dual-entry-style LedgerEntry/PlatformLedgerEntry tables, and the Transaction model genuinely encodes the 89/10/1-of-net-profit economic model (matched by transactionService.calculateDistribution). However, the database architecture is operated at an ad-hoc-to-repeatable maturity: there is NO prisma/migrations/ directory and the production deploy runs `prisma db push --accept-data-loss` on every Railway boot, which can silently drop columns/data across 97 models — a genuine, non-prerequisite-gated data-integrity time bomb. Other systemic gaps include domain enums modeled as free-text String with only code-comments (role, status, type, source — 28+ such fields, zero DB-level constraint), ~60% of Decimal money columns lacking explicit precision/scale, money stored as Float in the catalog/analytics models, dangling regionId strings with no FK to Region, no soft-delete/audit-trail convention, ~27 child tables with no createdAt, and significant model sprawl spanning ~12 loosely-related business domains. The schema reflects rapid accretion of features ahead of a disciplined data-platform foundation. With a migration baseline, enum hardening, money-type normalization, and an indexing pass it could reach a solid B+ before the September 2026 launch.

**Strengths**

- Core financial ledger is correctly Decimal-based: Transaction (grossAmount, discountAmount, nonprofitShare, platformFee, merchantNet, appliedCredits), Wallet.balance, CreditLedger, and LedgerEntry all use Decimal — avoiding float drift on money (schema.prisma:371-384, 404, 90, 420).
- The Transaction model genuinely matches the documented 89/10/1-of-net-profit economic model and is single-sourced to transactionService.calculateDistribution (server/src/services/transactionService.ts:49-54: nonprofitShare = netProfit*0.10, platformProfitShare = netProfit*0.01, merchantProfitShare = netProfit*0.89).
- Dedicated singleton treasury (PlatformAccount with fixed id 'gc-platform-treasury', @db.Decimal(18,4)) plus an append-only PlatformLedgerEntry with balanceAfter snapshots is a sound double-entry pattern for platform revenue (schema.prisma:431-453).
- The most-precision-sensitive money fields DO carry explicit @db.Decimal precision where it was thought about: PlatformAccount/PlatformLedgerEntry (18,4), DonationReceipt/TransactionRefund/CcvCampaign (10,2), affiliate commission rates (5,4), FiscalPolicy rates (5,4) — good intent on the newer models.
- Strong use of composite @@unique to prevent duplicate business facts: GroupMember(groupId,merchantId), PatronageRecord(coopId,merchantId,fiscalYear), ProposalVote(proposalId,voterId), TaxReportingFlag(merchantId,taxYear), DonorMilestone(userId,nonprofitId,milestone), RegionalMetric(regionId,period), StateStandingRecord(ein,registrationState).
- Hot-path indexes are present on the busiest tables: Transaction has @@index on neighborId/merchantId/nonprofitId/consumerState; Booking, AffiliateConversion, EmailRecipient, EmailCampaign, IrsNonprofitRecord all carry targeted indexes.
- Idempotency is modeled where it matters for payments: CatalogBilling.idempotencyKey @unique and WalletTopUp.stripePaymentIntentId @unique guard against double-charge/double-credit.
- Sensitive tokens are stored hashed, not plaintext: User.passwordHash, QrCheckoutToken.tokenHash @unique, MunicipalAccessToken.tokenHash @unique, WaitlistEntry.ipHash, CcvContract.contentHash (SHA-256 for contract immutability).

### Backend Architecture & Code Quality — Grade C (maturity 2/5)

The backend is a single Express 5 monolith (~20k LOC, 43 services / 35 controllers / 35 routes / 91 Prisma models) with a clean-on-paper controller-service-data shape, but the discipline is inconsistent: 29 of 35 controllers query Prisma directly (no repository/data layer), error handling is copy-pasted inline in 233 catch blocks while the central error handler in server.ts is dead code (zero next() calls), and raw error.message is returned to clients on the 500 path. There is no observability stack at all — no structured logging (only console.* in 31 files), no request IDs, no error monitoring (Sentry), and no metrics — which is disqualifying for a payments platform. Config is unmanaged: process.env is read ad hoc across ~40 files with no validation and unsafe defaults (JWT_SECRET falls back to 'default_secret'). TypeScript is not in strict mode and 300+ `any` usages erode type safety; the "build" only type-checks (noEmit) and prod runs uncompiled TS via tsx. Surface area is the dominant risk: CDFI packaging, FFIEC geocoding, DMS export, governance, data-coop, cooperative formation, AI loan underwriting (Gemini preview model), netting, and supply-chain matching are all shipped and largely untested (7 unit-test files, no backend CI, no money-path/webhook integration tests) for a September 2026 single-state launch. The feature-flag service is a genuine bright spot but is enforced in only 4 files, so most of that advanced surface is live, not gated. Several real correctness/security issues exist independent of the Stripe go-live prerequisites: non-idempotent webhook processing, 13 silent error swallows, and DB/migration safety (db push --accept-data-loss on every boot, no migrations dir).

**Strengths**

- Decimal.js (@prisma/client/runtime/library) is used consistently in the canonical split math (transactionService.calculateDistribution) and refundService, avoiding float drift, with a clearly-documented conservation model and a unit test asserting the balance sums to the cent.
- Money mutations are wrapped in prisma.$transaction (register, processTransaction, refundTransaction), and the refund ledger logic correctly debits merchant/treasury and credits the neighbor atomically with explicit ledger entries.
- FeatureFlagService is well-architected: typed flag interface, DB-backed with in-memory write-through cache, safe defaults on DB failure, and phased-rollout helpers (activatePhase3) — the right primitive for staged launch.
- Security baseline is present and correct: helmet, global apiLimiter + stricter authLimiter on login/register, bcrypt cost 12, JWT access(15m)/refresh(7d) split secrets, trust proxy in prod, raw-body webhook routes mounted before express.json(), and the admin test runner is gated behind authenticateToken + authorizeRole(['PLATFORM']).
- Prisma singleton pattern (lib/prisma.ts) prevents connection exhaustion in dev hot-reload; the integrity test runner exercises real endpoints through the full middleware stack; and tests use a real DB rather than mocking it, honoring the project's stated 'don't mock the DB' rule.
- Input validation uses Zod schemas at the controller boundary for most write endpoints (auth register, checkout preview, merchant/profile updates), with consistent 400 mapping of ZodError.

### Frontend UX — Grade C (maturity 2/5)

The SPA is visually polished, brand-distinctive, and surprisingly feature-complete across five roles, with thoughtful micro-touches (skeleton loaders, count-up animations, glass-box pricing reveal, milestone celebration modals, code-split lazy views). But the UX architecture is not enterprise-grade. The single largest gap is that there is no client-side router at all: all navigation is in-memory `activeView` state, so the browser back/forward buttons, deep links, page refresh, and shareable URLs (the app even references `/impact` and `/pay` that don't exist) are all broken. Navigation is buried entirely behind a hamburger menu even on desktop (the persistent desktop `NavBtn` is dead code), error states are largely swallowed to `console.error` with silent empty states, accessibility is near-absent (2 of 115 view/component files use any `aria-`; toasts aren't announced), and core surfaces diverge in design language (ProfileView is generic blue/gray Bootstrap-ish Tailwind vs the rest of the brand system). Production also double-loads Tailwind via the dev CDN. With routing, error-state, a11y, and consistency work this can reach B+; today it reads as a high-fidelity prototype rather than a launch-ready product.

**Strengths**

- Strong, consistent brand identity in the marketplace/wallet/order surfaces (purple #7851A9 / gold #C2A76F palette, italic-uppercase display type, generous rounded cards) gives the app a memorable, premium feel rare in marketplace MVPs.
- Loading and empty states are genuinely handled in the primary flows: MarketplaceView, OrderHistoryView, NonprofitSelectionView, and ImpactDashboardView all render skeleton shimmers while fetching and purpose-built empty states when there's no data.
- Code-splitting is done well: ~30 views/components are React.lazy'd with a branded Suspense spinner and per-view Framer Motion page transitions, which helps perceived performance despite the heavy app.
- Checkout flow is unusually transparent: CartDrawer shows the nonprofit disclosure with statutory commercial-co-venturer language, per-payment-method surcharge tags, live community-impact total, credit-redemption slider, and an insufficient-balance guard on the Place Order button.
- Merchant onboarding has a real first-run experience (MerchantWelcomeKit with a first-steps checklist, gated by a per-user localStorage flag) and a role-aware sidebar portal.
- Signup is role-aware with a 2x2 role picker, animated value-prop panel, inline password-match/length validation, and correct divergent flows (neighbor nonprofit-selection step, merchant onboarding handoff, CDFI admin-activation confirmation screen).
- Reduced-motion is respected in at least the Merchant portal sidebar (useReducedMotion), and the index.html includes a skip-to-content link with matching CSS plus iOS safe-area insets and PWA manifest/service-worker.

### Compliance & Legal/Regulatory Design — Grade C (maturity 3/5)

Good Circles has a genuinely sophisticated, above-MVP compliance DESIGN layer: a live IRS EO BMF verification pipeline (501(c)(3) good-standing + auto-revocation), a Commercial Co-Venturer (CCV) regime with state-specific filing deadlines, auto-generated co-venturer contracts, CT-6CF export, and a correct consumer-facing CCV disclosure at checkout; CAN-SPAM is well-engineered (suppression, hard-bounce/complaint handling, signed unsubscribe tokens, MARKETING-only physical-address gate, daily ceiling); 1099-K + INFORM Act thresholds are tracked; and PCI scope is correctly minimized via hosted Stripe Checkout (card data never touches the server, SAQ-A posture). However, the implementation has serious gaps that are NOT prerequisite-gated: the React app ships with ZERO legal pages (privacy/terms/cookies exist only on the marketing Astro site; an in-app link to /terms/catalog-upload resolves to the SPA fallback and 404s in-app), there is no consumer/neighbor terms-or-privacy consent capture at signup (only merchant onboarding has it), no data-subject deletion/DSAR/retention mechanism, and a systemic RBAC hole where the entire /api/compliance, /api/netting, and /api/credits surfaces are protected only by authenticateToken — so any logged-in Neighbor can export every merchant's Tax ID + email + gross sales (1099-K CSV) or trigger money-moving/expensive jobs. Accessibility/ADA is effectively unaddressed (3 aria-labels and 14 alt attributes across 115 components). The codebase also ships a full custodial stored-value wallet (real-money card top-up → internal balance → cash-out with a 3.5% conversion fee), transferable expiring credits, and merchant-to-merchant netting that move balances internally — directly contradicting the documented money-transmitter-avoidance constraint; the legal conclusion is SALT-consult-dependent (prerequisiteGated), but the design decision to ship custodial mechanisms is gradeable and currently unguarded.

**Strengths**

- IRS verification is real and production-grade: irsVerificationService.ts streams all 4 EO BMF national files, filters to 501(c)(3)/deductibility-1, stores ~300-400k records, and crucially cross-references revoked EINs against enrolled nonprofits to auto-strip isVerified (syncRevokedPlatformNonprofits, irsVerificationService.ts:231-261) so revoked orgs stop receiving donations — a true compliance control, not a checkbox.
- Consumer-facing CCV disclosure at point of sale is legally precise: CartDrawer.tsx:187 states 'No portion of the purchase price is tax-deductible for the consumer. Good Circles L3C is a commercial co-venturer and not a charitable organization' — exactly the framing CCV/charitable-solicitation law requires, and ComplianceService.generateDisclosureText (complianceService.ts:206-222) produces per-mechanism (PER_UNIT/FLAT/PERCENTAGE) text with EIN.
- CAN-SPAM engineering is strong: signed HMAC unsubscribe tokens (emailCampaignService.ts:245-258), suppression list enforced pre-send with fail-open safety, automatic suppression on hard-bounce/complaint via Resend webhook (emailCampaignService.ts:172-190), and a hard pre-flight block on mass MARKETING sends when EMAIL_PHYSICAL_ADDRESS is unset (emailCampaignService.ts:367-369).
- PCI scope correctly minimized: stripeService.createCheckoutSession uses hosted Stripe Checkout and wallet top-ups use PaymentIntents/Elements — no raw PAN/CVC ever stored or transmitted through the app (grep for cardNumber/cvc/pan returns nothing), keeping the platform in PCI SAQ-A territory.
- Entity-level compliance calendar is thorough and jurisdiction-aware: complianceService.ts STATIC_DEADLINES covers L3C annual reports across WY/MS/FL/GA/AL/LA, Alabama CCV registration renewal, Form 1065, FinCEN BOI review, monthly IRS EO BMF sync, and 1099-K issuance — with recurrence handling.
- Money-at-rest precision: all financial columns use Prisma Decimal (@db.Decimal(18,4)/(10,2)) and Decimal.js arithmetic throughout walletService/nettingService, avoiding float drift in regulated money math.
- Genuine data-coop anonymization: dataCoopService.collectAnonymizedData (dataCoopService.ts:105-113) emits only category/region/aggregate amounts with no user or merchant identifiers — real de-identification, not pseudonymization, and gated behind explicit opt-in (joinCoop/leaveCoop).
